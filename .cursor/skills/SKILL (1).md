# 系统化调试（seedpacespec-systematic-debugging）

## 引用约定

> **引用约定**：语义为主，编号为辅（加速定位），找不到不卡住。遵循 [`_shared/skill-interop.md`](./_shared/skill-interop.md)。

## 1. 目标与适用范围

### 1.1 目标

在修改业务代码或给出修复方案之前，基于可复核证据完成：**现象界定 → 根因分析 → 假设验证**。禁止仅凭猜测修改实现；禁止将未经验证的用户描述或 E2E 人工反馈直接等同于根因确认。

### 1.2 适用场景

| 场景 | 执行要求 |
|------|----------|
| 独立缺陷排查 | 按本文步骤 ①–⑥ 完整执行 |
| `seedpacespec-verify` 失败闭环 | 执行本文 ①–⑤（及授权时的 ⑥），并遵守 [verify 补充说明](../seedpacespec-verify/systematic-debugging.md) |
| apply 后发现异常 | 可先执行本文，再决定是否移交 sdx-apply |

### 1.3 加载顺序（强制）

1. 若由 verify 触发 → Read [verify 补充说明](../seedpacespec-verify/systematic-debugging.md)
2. 结论写入 `debug-report.md`（独立模式）或 `verify-report.md`（verify 模式）；verify 对用户仅交付报告路径及一句结论

---

## 2. 铁律与方法论约束

```
未完成「现象界定 + 证据齐备 + 分析有据 + 可自证项已自证」，不得确认根因，不得修改业务代码
```

| 约束 | 说明 |
|------|------|
| 步骤 ①–④ | 完成后方可进入步骤 ⑤（假设验证）；verify「仅报告」模式可于 ⑤ 前停止 |
| 调试方式 | **不依赖断点**；以日志、自动化测试、脚本、Read/Grep 静态分析梳理**执行路径** |
| 验证优先级 | Agent 可执行的验证（脚本/单测/命令复现）优先；用户代测仅于步骤 ① 已判定不可自测时启用 |

---

## 3. 流程总览

```
① 现象界定与验证策略（可自测 → Agent 执行；不可自测 → 用户行动指示单 + 可选诊断日志）
        ↓
② 证据材料采集（日志、报错、截图等；缺失项 AskQuestion）
        ↓
③ 根因分析（材料分析 → 逻辑推演 → 业务分层日志 / 第三方检索 → 必要时读第三方源码）
        ↓
④ 代码执行路径梳理（Read/Grep，静态分析）
        ↓
⑤ 假设提出与验证（自证优先；用户反馈仅作补充）
        ↓
⑥ 最小修复与复验
```

---

## 4. 根因分类（通用枚举）

| 分类 | 定义 |
|------|------|
| `implementation-bug` | 本仓库业务实现与预期行为不一致 |
| `test-bug` | 测试用例、断言或测试环境与规格不一致 |
| `config-env` | 环境、配置、权限或依赖服务导致无法完成判定 |
| `third-party` | 第三方组件缺陷或本仓库集成用法错误 |
| `spec-gap` | 需求/规格与实现或测试不一致 |
| `unknown` | 步骤 ①–⑤ 完成后仍无法得出高置信结论（须记录证据缺口） |

verify 场景使用 `prd-drift` 等分类，定义见 [verify 补充说明](../seedpacespec-verify/systematic-debugging.md)。

---

## 5. 步骤 ①：现象界定与验证策略

### 5.1 现象信息采集

通过 AskQuestion 或结构化澄清，将下列内容写入 **现象记录**：

| 字段 | 采集内容 |
|------|----------|
| 触发条件 | 页面/模块、操作序列、输入数据 |
| 实际结果 | 可观察现象（含 UI、返回值、状态） |
| 预期结果 | 用户陈述或 PRD 规定 |
| 复现规律 | 必现 / 偶现 / 特定账号或数据集 |
| 时间范围 | 首次出现时间、是否与发布或配置变更相关 |

⛔ 用户口述仅作调查线索，**不得**直接作为已确认根因。

### 5.2 验证策略分支

| 条件 | Agent 行为 |
|------|------------|
| **本环境可复现**（CLI 测试、单测、HTTP 探测、本地运行等） | 构造最小复现：补充/执行测试、一次性脚本、失败用例；输出归档至现象记录 |
| **本环境不可复现**（真机、内网、生产账号、专用硬件等） | 出具 **用户行动指示单**（模板见本文「用户行动指示单」章节，默认 5.3）；必要时植入 **临时诊断日志**；要求用户回传指定 **产物** |

### 5.3 用户行动指示单（不可自测时强制）

须写入报告，至少包含：

```markdown
## 用户验证行动指示

1. 操作步骤：（与现象记录一致的逐步说明）
2. 预期结果：…
3. 实际结果（由用户填写）：…
4. 须提交产物：（勾选）
   - [ ] 完整运行日志（控制台 / logcat / Xcode，自启动至异常）
   - [ ] 错误界面或弹窗截图（含完整文案）
   - [ ] CI 构建标识或 artifacts 路径
5. 若已植入诊断日志：请在分支 `{branch}` 构建运行后，回传含 `[DEBUG]` 的日志片段
```

⛔ 禁止在未提供操作步骤、产物清单及（如适用）日志点位的情况下，要求用户执行 E2E 并口头反馈即视为验证完成。

---

## 6. 步骤 ②：证据材料采集

在步骤 ① 完成后，对下列材料进行 **主动索取**（缺失项列入 AskQuestion）：

| 材料类型 | 分析用途 |
|----------|----------|
| 运行日志 | 定位首条异常、时间线、关联请求标识 |
| 报错信息 | 堆栈、错误码、异常类型；检索代码与外部 issue |
| 现象截图 | 校验 UI 状态与口述一致性 |
| 测试/CI 输出 | 作为代码定位入口 |

**现象记录**须同步更新：

- 现象 / 预期 / 实际 / 复现步骤 / 稳定性  
- 证据来源（用户日志、截图、Agent 自测输出等）  
- **验证策略**：自测（命令） / 用户代测（行动指示单编号）  

关键材料缺失 → AskQuestion；索取后仍缺失 → 标注 `证据缺口`，**不得**进入步骤 ③ 作出根因定论。

---

## 7. 步骤 ③：根因分析（由浅入深）

按序执行；上一层已得出高置信结论时，不强制进入下一层。

### 7.1 基于现有材料（优先）

在不修改业务逻辑的前提下分析：

| 输入 | 分析要点 |
|------|----------|
| 日志 | 时序、首条 ERROR、跨层请求关联 |
| 现象截图 | UI 状态是否支持特定失败模式（未登录、空态、错误文案等） |
| 复现规律 | 必现倾向主路径/配置；偶现倾向竞态、超时、脏数据 |

### 7.2 逻辑推演

在已读代码与已确认事实基础上推理，须符合可验证规律（因果序、状态机、网络/异步约束、权限与环境）：

- 记录格式：「观察 P；已知 Q；依据规律 R，推测 S」  
- 标注置信度：`高` / `中` / `低`  
- **低置信**不得直接进入修复；须经步骤 7.3/7.4 或步骤 ⑤ 验证

### 7.3 指向本仓库业务代码

**典型信号**：I/O 与预期不符、流程结果异常、堆栈位于本仓库。

1. Read/Grep 失败路径（配合步骤 ④）  
2. 在关键 **输入/输出边界** 植入临时诊断日志（入参、出参、分支、错误码）  
3. **可自测**：执行复现命令，依据日志将异常收敛至具体层级  
4. **不可自测**：更新用户行动指示单，要求在同分支运行并回传 `[DEBUG]` 日志  

分层日志示例：

```
[L1 入口] in=...
[L2 业务] in=... out=... branch=...
[L3 远程/存储] req=... res=... err=...
→ 异常区间：L2→L3
```

可与 **对照分析** 结合：选取同模块正常路径，列出差异（含 `path:line`）。

### 7.4 指向第三方组件

**典型信号**：堆栈位于依赖包、版本变更后引入、API 用法与文档不符。

| 顺序 | 动作 | 说明 |
|------|------|------|
| 1 | 确认依赖版本 | lockfile / `pubspec` / `package.json` / `pom.xml` |
| 2 | [GitHub Issues](https://github.com) | 仓库 + 错误关键词 |
| 3 | [Stack Overflow](https://stackoverflow.com) | 错误 + 库名 + 版本 |
| 4 | 官方 changelog | 破坏性变更 |
| 5 | Read 第三方源码 | **仅在前述步骤无法定论时**；仍须结合日志与规律，非断点调试 |

外部平台存在已知 issue 时，**须**引用链接作为依据；否则再读源码核对集成误用。

### 7.5 规格对照（verify 或已提供 PRD/需求时强制）

判定偏差属于实现、测试、环境还是规格缺口。

---

## 8. 步骤 ④：代码执行路径梳理

针对本仓库业务代码或步骤 7.4 中不得已分析的第三方源码，采用 **静态分析** 梳理执行路径：

1. 自入口（堆栈、路由、测试步骤）经 Read/Grep 构建 **调用链**  
2. 标注：条件分支、异步等待点、外部 I/O、状态变更  
3. 与日志及推演结论对照，定位最可能产生现象记录中「实际结果」的节点  
4. 报告输出：**执行路径摘要**（`path:line` + 行为说明）

⛔ 不得将「建议人工断点调试」作为 Agent 交付结论；须给出基于路径与证据的分析判断。

---

## 9. 步骤 ⑤：假设提出与验证

### 9.1 假设陈述

单一假设，格式：「根因为 **X**，依据 **Y**」（Y 指向执行路径、日志、issue 或推演链）。

### 9.2 验证优先级（强制）

| 优先级 | 手段 | 适用条件 |
|--------|------|----------|
| 1 | Agent 可执行验证 | 单测、最小脚本、`curl`、复现命令、单变量对比实验 |
| 2 | 静态代码核对 | 分支可达性、类型/空值与日志一致性 |
| 3 | 用户按行动指示单反馈 | 仅当步骤 ① 已判定不可自测；且须具备明确步骤与日志点位 |

⛔ 禁止：未执行优先级 1/2 即要求用户 E2E 验证，并将口头反馈视为根因已确认。  
⛔ 禁止：假设未验证即进入步骤 ⑥。

### 9.3 结果处置

| 结果 | 后续动作 |
|------|----------|
| 验证成立 | 可进入 [步骤 ⑥](#10-步骤-修复与复验) |
| 验证不成立 | 提出新假设，回退至步骤 ③ 或 ② 补充材料 |
| 无法自证且用户未反馈 | 分类 `unknown`，标注 `证据缺口`，不得标记为已确认根因 |

**步骤 ③–⑤ 完成条件：** 现象记录完整、执行路径摘要已输出、假设已记录，且具备至少一项自证证据（或已签发行动指示单并标注「待用户验证」）。

---

## 10. 步骤 ⑥：修复与复验

1. **变更范围**（建议经用户确认）：变更项 / 排除项 / 影响面  
2. **最小修复**：仅针对已验证根因；移除临时 `[DEBUG]` 日志（除非规格要求保留可观测性）  
3. **复验**：先执行失败用例，再执行相邻冒烟；**优先 Agent 本地/CI 执行**  
4. **修复失败**：独立模式第 3 轮后停止并 AskQuestion；verify 模式最多 2 轮，见 [verify 补充说明](../seedpacespec-verify/systematic-debugging.md)

---

## 11. 用户协作（证据不足时）

与步骤 ①（不可自测）、②（材料缺失）衔接：

| 情形 | 要求 |
|------|------|
| 行动指示单已发出，用户未反馈 | 报告标注「待用户验证」；根因不得标为已确认 |
| 用户补充日志/截图 | 更新现象记录，继续步骤 ③ |
| 永久不可自测 | 行动指示单 + AskQuestion；结论上限为 `unknown` 或「高置信，待用户确认」 |

---

## 12. 红线

| 编号 | 禁止行为 |
|------|----------|
| R1 | 现象未界定即提出根因或修改代码 |
| R2 | 本环境可复现却未执行测试/脚本，转由用户代测 |
| R3 | 未索取日志、报错、截图等关键材料 |
| R4 | 第三方问题未检索 GitHub Issues / Stack Overflow 即修改业务代码 |
| R5 | 无执行路径摘要、无证据链即下结论 |
| R6 | 假设未经步骤 ⑤ 验证即修复 |
| R7 | 以用户 E2E 口头反馈替代 Agent 自证 |
| R8 | 单次变更涉及多个无关模块 |

verify 场景附加红线见 [verify 补充说明](../seedpacespec-verify/systematic-debugging.md)。

## 13. 产出模板

### 13.1 独立模式 — `debug-report.md`（可选）

```markdown
# 调试报告

## ① 现象与验证策略
- 现象记录
- 自测命令 / 用户行动指示单

## ② 证据材料
- 日志 / 报错 / 截图摘要

## ③④ 分析与执行路径
- 材料分析 / 逻辑推演 / 分层日志 / 第三方检索
- 执行路径摘要（path:line）

## ⑤ 假设与验证
- 假设 | 自证记录 | 用户反馈（如有）

## 根因结论
- 分类 | 陈述

## ⑥ 修复与复验（如已执行）
```

### 13.2 verify 模式

见 [verify 补充说明·报告根因章节](../seedpacespec-verify/systematic-debugging.md#6-报告里根因分析怎么写)（`/sdx-verify` 的报告模板中「根因分析」章节）。

## 14. 速查

| 步骤 | 主要活动 | 完成条件 |
|------|----------|----------|
| ① | 现象界定；确定自测或用户行动指示单 | 现象记录 + 验证策略 |
| ② | 采集日志/报错/截图 | 材料齐备或标注缺口 |
| ③ | 材料分析、推演、分层日志或第三方检索 | 具备分析结论 |
| ④ | 执行路径静态梳理 | 路径摘要 |
| ⑤ | 假设 + 自证（优先） | 验证成立或待用户 |
| ⑥ | 最小修复 + 复验 | 失败项消除 |
