## Context

本项目为全新搭建的 macOS Electron 桌面应用，实现基于触摸板检测的临时按键层功能。用户单指放在触摸板上时，主键盘进入自定义层（Layer 2），将 `i/k/j/l` 等键映射为方向键等功能。

### 关键约束

1. **平台限制**：仅支持 macOS 10.15+，需 Accessibility 权限获取全局按键事件
2. **触摸板检测**：必须通过 macOS IOKit/NSEvent API 监听触摸板原始事件
3. **性能基线**：触摸板检测延迟 < 100ms，按键映射延迟 < 50ms
4. **资源约束**：后台运行内存占用 < 100MB
5. **UI 约束**：配置界面简洁，菜单栏图标需适配 macOS 深色/浅色模式

## 技术选型与决策

### D01: 触摸板检测方案 `[架构级]`

**选择**：使用 `@nstudio/nativescript-mac-messages` + 原生 macOS IOKit 封装

**备选方案**：

| 方案 | 优点 | 缺点 |
|------|------|------|
| A: 纯 Electron `globalShortcut` | 跨平台，API 简单 | 无法检测触摸板事件，只能监听键盘 |
| B: Node-ffi 直接调用 IOKit | 无需额外依赖，控制精细 | 需要维护 C 绑定，开发复杂度高 |
| C: 使用 `iohook` 库 | 社区成熟，已封装 | 触摸板支持有限，主要面向键盘鼠标 |
| **D: 自定义 N-API 模块封装 IOKit** | 专为触摸板设计，性能最优，可精确检测多指 | 需要编写原生代码，项目复杂度增加 |

**理由**：触摸板检测是本应用的核心能力，需要精确的单/多指区分和实时状态通知。通用库无法提供足够细粒度的触摸板事件。选择自定义原生模块方案，封装 macOS `MTDevice` 和 `IOKit` 接口，通过 N-API 暴露给 Node/Electron 层。

### D02: 全局按键拦截方案 `[架构级]`

**选择**：使用 macOS `CGEventTap` 通过 `node-global-key-listener` + 自定义补丁

**备选方案**：

| 方案 | 优点 | 缺点 |
|------|------|------|
| A: `iohook` | 跨平台，API 统一 | 在 macOS 上需要 Accessibility 权限，且事件延迟较高 |
| B: Electron `globalShortcut` | 官方 API，集成简单 | 只能注册快捷键，无法拦截普通按键 |
| **C: 基于 `CGEventTap` 的原生实现** | macOS 原生方案，延迟最低，可拦截和修改任意按键 | 仅支持 macOS，需要原生代码 |

**理由**：应用需要在 Layer 2 期间拦截并修改普通按键事件（如 `i` → `↑`），而非仅监听快捷键。`CGEventTap` 是 macOS 上唯一能提供此能力的原生 API。选择包装好的 N-API 模块方案。

### D03: 按键映射引擎设计 `[模块级]`

**选择**：状态机驱动的轻量级映射引擎，主进程处理，渲染进程仅 UI

**理由**：
- 触摸板状态和按键拦截都在主进程（原生模块绑定限制）
- 映射逻辑简单（单键映射，无组合键），无需复杂规则引擎
- 状态机明确区分 Layer 1/2，避免条件分支混乱

### D04: 配置持久化方案 `[模块级]`

**选择**：JSON 文件存储在 `~/Library/Application Support/touchpad-keymap-layer/`

**理由**：
- 配置量小（键值对列表），无需数据库
- JSON 人类可读，便于用户手动编辑
- 使用 Electron `app.getPath('userData')` 获取标准路径

### D05: 配置界面技术栈 `[模块级]`

**选择**：HTML + Vanilla JS + 轻量 CSS（或 Vue 3 Composition API）

**理由**：
- 界面简单（列表增删改），无需复杂状态管理
- 减少构建体积，加快启动速度
- 若后续需要复杂交互，可平滑迁移到 Vue/React

## 模块总览

本项目为全新搭建，基于 Electron + TypeScript 桌面应用标准分层架构，采用以下通用层：
- **表现层**：用户界面（配置窗口、菜单栏图标）
- **业务逻辑层**：按键映射引擎、触摸板状态机
- **基础设施层**：原生模块封装、配置存储、日志

### 功能点

| 编号 | 功能 | PRD 对应 | 优先级 | 实现模块 |
|------|------|----------|--------|----------|
| F01 | 单指触摸板检测与层切换 | R01 | P0 | TouchpadMonitor + 状态机 |
| F02 | 按键拦截与单键映射 | R02 | P0 | KeyInterceptor + 映射引擎 |
| F03 | 映射规则 JSON 持久化 | R03 | P0 | 配置管理器 |

### 非功能点

| 编号 | 要求 | 设计上如何满足 |
|------|------|---------------|
| NF01 | 触摸板检测延迟 < 100ms | TouchpadMonitor 使用 IOKit 直接回调，不经过轮询；状态机同步处理，无异步延迟 |
| NF02 | 按键映射延迟 < 50ms | KeyInterceptor 在主进程同步处理，映射引擎规则使用 Map 查找 O(1)；注入使用 CGEvent 原生 API |
| NF03 | 内存占用 < 100MB | 无冗余进程，渲染进程按需启动（仅配置窗口打开时）；主进程轻量，无大型依赖 |
| NF04 | macOS 深色/浅色模式适配 | 菜单栏图标提供两套模板图片，根据 `nativeTheme` 动态切换 |
| NF05 | Accessibility 权限友好提示 | 首次启动检测权限状态，未授权时弹出引导对话框，提供跳转系统设置按钮 |

### 约束

| 编号 | 约束 | 如何影响设计 |
|------|------|-------------|
| C01 | 仅支持 macOS | TouchpadMonitor、KeyInterceptor、KeyInjector 均为 macOS 原生模块，不进行跨平台抽象 |
| C02 | 需 Accessibility 权限 | 应用在权限未获取时优雅降级：继续运行但提示用户，不崩溃；配置界面可查看权限状态 |
| C03 | Electron 主/渲染进程隔离 | 所有原生模块绑定在主进程；渲染进程通过 IPC 调用配置 API；触摸板状态通过 IPC 推送到菜单栏 |
| C04 | 触摸板事件低层 API | 使用 IOKit 的 `MTDevice` 私有接口或 `NSEvent` 全局监听，需要在原生模块中处理 |
| C05 | 按键事件系统级拦截 | 使用 `CGEventTap` 必须创建在单独线程，需要在原生模块中管理事件循环和线程安全 |

## 核心模块设计

### 触摸板状态机 (TouchpadStateMachine)

- **为什么需要这个模块**：触摸板层切换是全局状态，影响按键映射行为。需要集中管理状态转换逻辑（Layer 1 ↔ Layer 2），避免分散在多个组件中导致不一致。

- **边界**：
  - **管**：单指触摸检测阈值判断、层状态维护、状态变更通知
  - **不管**：具体按键如何映射（交给映射引擎）、触摸板硬件细节（交给原生模块）

- **协作关系**：
  - 从 `TouchpadMonitor` 接收原始触摸事件
  - 向 `KeymapEngine` 提供当前层状态查询
  - 向 `TrayIcon` 发送状态变更通知以更新图标

- **关键设计取舍**：
  - 选择**同步状态推送**而非轮询：触摸板事件触发时立即更新状态，确保按键事件发生时层状态已就绪
  - 代价是状态机必须在主线程处理，但触摸板事件频率低，不会造成阻塞

### 按键映射引擎 (KeymapEngine)

- **为什么需要这个模块**：按键拦截和映射逻辑需要与业务状态（层状态、配置规则）解耦，独立管理规则匹配和按键注入。

- **边界**：
  - **管**：规则加载/缓存、拦截决策、按键注入调用
  - **不管**：触摸板如何检测（依赖状态机）、配置如何存储（依赖配置管理器）

- **协作关系**：
  - 从 `KeyInterceptor` 接收待拦截按键事件
  - 向 `TouchpadStateMachine` 查询当前层状态
  - 向 `ConfigManager` 查询映射规则
  - 调用 `KeyInjector` 执行模拟按键

- **关键设计取舍**：
  - 选择**运行时规则缓存**：配置变更时重建 Map，查询 O(1)
  - 放弃**正则/通配符支持**：当前仅单键映射，保持简单；后续可扩展

### 原生模块层 (Native Modules)

- **为什么需要这个模块**：Electron 无法直接访问 macOS 低层触摸板和按键事件 API，必须通过 N-API 绑定原生代码。

- **边界**：
  - **TouchpadMonitor**：仅暴露触摸开始/结束事件，不暴露原始坐标（减少数据传输）
  - **KeyInterceptor**：仅暴露按键码，不暴露完整事件对象（减少上下文切换开销）
  - **KeyInjector**：仅支持标准按键码，不支持复杂组合键（简化实现）

- **协作关系**：
  - 通过 N-API 暴露给 Node.js 主进程
  - 内部管理 macOS 事件循环线程，与 Node.js 事件循环隔离

- **关键设计取舍**：
  - 选择**三个独立模块**而非一个通用模块：职责分离，降低单个模块复杂度
  - 代价是编译产物增多，但调试和维护更简单

### 配置界面 (Settings UI)

- **为什么需要这个模块**：用户需要可视化界面管理映射规则，而非手动编辑 JSON。

- **边界**：
  - **管**：表单展示/提交、列表渲染、用户反馈
  - **不管**：配置存储细节、数据验证规则（交给配置管理器）

- **协作关系**：
  - 通过 IPC 调用 `ConfigManager` 的 CRUD API
  - 通过 IPC 查询 Accessibility 权限状态

- **关键设计取舍**：
  - 选择**Vanilla JS 实现**：界面简单（一个列表+表单），无需框架开销
  - 保留**Vue 迁移路径**：文件结构预留 Vue 组件化空间（data/component 分离）

## 本设计的优缺点

### 优点

1. **职责分离清晰**：触摸板检测、按键映射、配置管理各自独立，便于单元测试和后续扩展
2. **原生性能最优**：触摸板和按键事件直接走原生 API，无 Electron 层延迟
3. **状态机明确**：Layer 1/2 状态集中管理，避免条件分支散落在各组件
4. **模块可扩展**：三个原生模块独立，后续可单独升级或替换实现

### 已知局限 / 缺点

1. **平台绑定深**：三个核心原生模块均为 macOS 专用，未来跨平台需完全重写
2. **原生代码维护成本**：需要理解 macOS IOKit 和 CGEvent API，调试复杂
3. **线程安全风险**：`CGEventTap` 运行在独立线程，与 Node.js 主线程交互需要仔细管理
4. **权限用户体验**：Accessibility 权限申请是系统级阻塞操作，首次体验可能不佳

### 后续演进方向

- 若后续支持 Windows，需要重写三个原生模块为 Windows API 版本
- 若后续支持组合键映射（如 `Cmd+i` → `Cmd+↑`），需要扩展 KeymapEngine 规则引擎和 KeyInjector API
- 若后续支持多场景层配置（如「编码模式」「写作模式」不同映射），需要扩展状态机支持多 Layer 定义

## Risks / Trade-offs

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 原生模块编译失败 | 阻塞开发，无法调试 | 提供预编译二进制；Docker 化编译环境；CI 自动构建 |
| Accessibility 权限被拒 | 应用无法拦截按键，核心功能失效 | 优雅降级（仅触摸板检测可用）；首次启动强引导授权 |
| CGEventTap 线程崩溃 | 应用崩溃，数据丢失 | 原生模块添加异常边界；主进程守护重启；错误日志上报 |
| 触摸板检测误判（多指误触发） | 用户体验差，层切换错乱 | 严格单指判断逻辑（接触点数量=1）；添加灵敏度调节配置 |
| 按键注入被安全软件拦截 | 映射失效 | 引导用户添加应用白名单；提供诊断工具检查注入状态 |
| 配置 JSON 损坏 | 启动失败 | 配置加载时添加 try/catch；损坏时自动重置默认并备份旧文件 |
